# Аудит склада ERP — 27.10.2026

Документ является **планом**, а не разрешением исправить старые остатки. Промышленная БД и текущие заказы не подлежат автоматическому пересчёту.

Важно: хотя заказ ЗП-000039 позволяет восстановить список артикулов, у нескольких строк одинаковое количество. Поэтому **по одному количеству нельзя безопасно сопоставить каждую строку старой приёмки с конкретным артикулом**. Нельзя просто массово перенести 450 шт. в перепродажу без однозначных ключей.

## Исправление возникновения новых ошибок

Миграция `supabase/migrations/20261027_receipt_safety.sql`:

1. Добавляет `NOT VALID` ограничение: **новые** движения склада не могут быть без идентификатора соответствующего типа. Исторические строки остаются как были.
2. Останавливает удаление приёмки с оставшимися складскими движениями.
3. Не разрешает менять количество, товар или цену проведённой приёмки.
4. Не позволяет добавлять движения по отсутствующей или уже проведённой приёмке.
5. Добавляет атомарную серверную функцию `post_supplier_receipt_safe(uuid)`, которая берёт блокировку на документ, проверяет строки и типы, распределяет доставку, обновляет закупочные цены, вносит движения и проводит документ **в одной транзакции**.

Фронтенд `ReceiptModal.tsx` вызывает RPC; опасные кнопки скрыты у проведённых приёмок. `RelatedDocumentModal.tsx` отказывает в создании приёмки из заказа с потерянным товарным ID.

**Порядок внедрения:** сначала применить миграцию, проверить защиту и RPC на тестовых строках в транзакции с `ROLLBACK`; затем объединить PR после успешной сборки; проверить Netlify и номер сборки. Если серверная миграция не применяется, **не объединять** фронтенд с RPC, иначе проведение приёмок перестанет работать.

## Пошаговая проверка после миграции (без опасных исправлений)

- Перепроверить состояние до и после: количество строк движений, суммы по типам, резерв этикеток и список незавершённых заказов должны остаться без изменений.
- Создать тестовую приёмку и её строки **внутри транзакции**, провести через `post_supplier_receipt_safe`, проверить: одна запись поступления на строку, статус `posted`, корректное распределение доставки, нужный `item_id` или `product_id`. Выполнить `ROLLBACK`.
- В отдельной транзакции попробовать провести строку `resale_product` без `item_id`; убедиться, что RPC отклоняет проведение и не изменяет остатки. Выполнить `ROLLBACK`.
- Проверить повторный вызов RPC после успешного проведения: должен отвергаться без дублей. Выполнить `ROLLBACK`.
- Проверить, что изменение количества у проведённой приёмки и прямое удаление приёмки с движениями отвергаются.
- Проверить текущие производственные задания и печать: изменения **не должны затрагивать** операции выпуска пачек.

3. Для 15 движений удалённых документов определить первоначальный документ и фактическое наличие товара. Не считать автоматически, что товар физически отсутствует или присутствует.

## Контрольные SQL-запросы только для чтения

```sql
SELECT item_type, count(*) AS rows, sum(quantity_on_hand) AS qty
FROM public.stock_available
GROUP BY item_type
ORDER BY item_type;

SELECT count(*) AS orphan_rows, sum(quantity) AS orphan_qty
FROM public.stock_movements
WHERE item_type = 'product' AND product_id IS NULL;

SELECT count(*) AS old_active_label_reservations, sum(sr.quantity) AS qty
FROM public.stock_reservations sr
JOIN public.production_orders po ON po.id = sr.production_order_id
JOIN public.consumables c ON c.id = sr.consumable_id
WHERE sr.status = 'active' AND po.status = 'done' AND c.article = 'этикетки';

SELECT count(*) AS missing_receipt_movements
FROM public.stock_movements sm
LEFT JOIN public.supplier_receipts r ON r.id = sm.source_document_id
WHERE sm.source_document_type = 'supplier_receipt'
  AND sm.source_document_id IS NOT NULL
  AND r.id IS NULL;
```
